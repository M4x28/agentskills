The optional `parameters` frontmatter key lets supporting clients render a guided prompt template when a user invokes your skill via `/skill-name`. Each required and optional parameter appears as an inline field — pre-filled with defaults where available — before the model ever sees the message.

<Note>
`parameters:` is a backwards-compatible extension. Clients that do not implement it safely ignore the key and invoke the skill normally.
</Note>

## Schema

````markdown SKILL.md
---
name: your-skill
description: What the skill does and when to invoke it.
parameters:
  required:
    - name: param_name
      description: "Human-readable hint shown to the user (<=120 chars)"
  optional:
    - name: another_param
      description: "What this optional input controls"
      default: "sensible default"
---
````

### Fields

| Field | Required | Notes |
|-------|----------|-------|
| `parameters` | No | Omit entirely for skills with no parameters. |
| `parameters.required` | No | Parameters the skill needs to produce useful output. |
| `parameters.optional` | No | Parameters that improve output quality but have working defaults. |
| `name` *(per param)* | Yes | Snake_case identifier, e.g. `company_name`. Max 64 characters. |
| `description` *(per param)* | Yes | Shown as an inline hint in the UI. Max 120 characters. |
| `default` | No | Optional params only. Always a string; the model interprets the type. |

### Rules

- `name` must be unique across both `required` and `optional` within a skill.
- `description` must be 1–120 characters.
- `default` may only appear on `optional` parameters.
- Skills with no parameters omit `parameters:` entirely.
- Display order in the UI follows the order declared in the YAML.

## How supporting clients behave

When a user types `/skill-name` in a supporting client:

1. The client parses the `parameters:` block from the skill's frontmatter.
2. A guided template appears inline in the chat input — required parameters as empty highlighted fields, optional parameters pre-filled with their `default` values, each with its `description` as an inline hint.
3. The user fills in values and submits. The composed message is sent normally; the SKILL.md body is injected as skill context as usual.

## Fallback for non-supporting clients

Add a `## Parameters` section to your SKILL.md body. The model reads it and prompts the user interactively for any missing inputs, providing the same information through a conversational turn instead of a guided UI.

````markdown SKILL.md
## Parameters

**Required**
- `topic` — Main subject or title of the presentation

**Optional**
- `slides` — Number of slides to generate (default: 10)
- `audience` — Target audience: executives | engineers | students | general
````

## Example

The `pptx` example skill uses `parameters:` with one required and two optional inputs:

````markdown examples/pptx/SKILL.md
---
name: pptx
description: >
  Creates a PowerPoint presentation (.pptx) from a topic description.
  Use when the user asks to "make a presentation", "create slides", or mentions .pptx.
parameters:
  required:
    - name: topic
      description: "Main subject or title of the presentation"
  optional:
    - name: slides
      description: "Number of slides to generate"
      default: "10"
    - name: audience
      description: "Target audience (e.g. executives, engineers, students)"
---
````

See [`examples/pptx/SKILL.md`](https://github.com/agentskills/agentskills/tree/main/examples/pptx/SKILL.md) for the complete implementation.

## Validation

The [skills-ref](https://github.com/agentskills/agentskills/tree/main/skills-ref) reference library validates `parameters:` blocks along with the rest of your frontmatter:

```bash
skills-ref validate ./my-skill
```

It checks that parameter names match the allowed character set, descriptions are within the length limit, and no names are duplicated across `required` and `optional`.
